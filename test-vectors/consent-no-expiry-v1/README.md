# Consent without expiry and execution reasons, v1

These additive served vectors leave every existing corpus byte-identical. Requests
run through Cingulate's real handler against scratch SQLite stores. Success files
are untouched handler response bytes; refusal files encode the handler's transport
error as `{"error":{"code":...,"message":...}}`. Stored JSON uses the durable
record serialization. The clock begins at 10000 ms.

`no-deadline-request.json` omits `expires_in_ms`. Requesters may do this only after
`catalog.list` advertises `consent-no-expiry/v1`; older Cingulate rejects omission.
The stored, requester and phone records omit expiry fields. A future get at
10000010000 ms is still pending and can be answered normally.

All pending cards are ordered **oldest first by creation time, then id**, with no
expiry-based priority. `mixed-list-page` puts a no-deadline card (created 10000)
before a deadline card (created 10010, expires 11010), then another no-deadline
card (created 10020). `mixed-list-continued` resumes after the middle card with
the new JSON object cursor `{created_at_ms, elicitation_id}`. Cingulate also
accepts the previous `{expires_at_ms, elicitation_id}` cursor for one release,
resolving its card's creation position; callers copy returned objects unchanged.

`execution-reason` reports `approved_not_executed` with `session_ended`, which
appears as `execution_reason` on requester records and `executionReason` on the
phone. The reason-code set is open: Cingulate accepts and stores any well-formed code, not only the documented ones. `reason-with-executed` and `malformed-reason`
are refused without changing the report.

Regenerate/check from the workspace root:

```sh
cargo run -p cingulate-vectors --example generate_no_expiry_vectors --locked
cargo run -p cingulate-vectors --example generate_no_expiry_vectors --locked -- --check
```

`SHA256SUMS` covers every request, reply, stored record and this README. The served
integration test independently pins that manifest and compares regenerated bytes.
